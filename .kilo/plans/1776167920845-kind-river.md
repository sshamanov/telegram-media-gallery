# Container And Playwright Execution Plan

## Decision
- Keep the application lineage on `node:20-alpine` for dev and future production runtime.
- Add a production-oriented repo `Dockerfile` based on `node:20-alpine`.
- Keep the existing convenience dev flow in `docker-compose.yml` for now: `npm install && npm run dev`.
- Add a separate Playwright-ready test service in the same compose file, using a Debian-based Playwright image.
- Playwright must use the web server started by the dev `app` container.
- In containerized test runs, Playwright must not start any app process itself; its `webServer` integration must be disabled for that mode.
- Keep the current Playwright spec files for now and fix container/runtime execution first.

## Why
- The current repo has only a dev container in `docker-compose.yml` and no production `Dockerfile`, so application runtime requirements are not tracked in-repo yet.
- `node:20-alpine` is acceptable for the app container lineage, but browser automation dependencies do not fit well there.
- Browser installation failed because Playwright needs Debian/Ubuntu-style runtime libraries that do not match the current Alpine app container.
- A dedicated Playwright container isolates browser tooling from the app runtime and avoids polluting the Alpine app image.
- Using the dev container's server as the only web server in test runs keeps responsibilities clear and avoids duplicate process startup.

## Current State
- `docker-compose.yml` defines a single `app` service using `node:20-alpine`.
- The `app` service bind-mounts the repo and runs `npm install && npm run dev -- --host 0.0.0.0 --port 5173`.
- No repo `Dockerfile` exists.
- `playwright.config.ts` currently contains a `webServer` block that starts `npm run dev`.
- `package.json` points `test:short`, `test:long`, and `test:all` to Playwright.
- Real Playwright spec files already exist, but execution is blocked by browser/container environment mismatch.

## Target Architecture

### App / Dev / Runtime Lineage
- The app stays on `node:20-alpine`.
- The repo gains a production-oriented `Dockerfile` based on `node:20-alpine`.
- That Dockerfile should be production-like, not a dev shell image:
  - install the actual runtime packages needed by the app image
  - install Node dependencies in image build steps
  - build the app
  - serve static output with an explicit static server command
- The exact runtime package list can be refined later, but the file should establish the correct production image shape now.

### Dev Container
- Keep `app` in `docker-compose.yml` as the fast convenience container.
- Keep the current startup behavior for now: `npm install && npm run dev`.
- Keep the repo bind mount for fast iteration.
- Keep host networking behavior aligned with current project rules.

### Playwright Test Container
- Add a second service in `docker-compose.yml` dedicated to Playwright only.
- Use a Playwright-ready Debian-based image for this service.
- Bind-mount the same repo into the test container.
- Do not start Vite, npm dev, or any extra helper service inside the Playwright container.
- The Playwright container should only run test commands against the already-running app service.

### Server Ownership During Tests
- The dev `app` container owns the web server.
- The Playwright container connects to that server and runs tests only.
- Playwright `webServer` should be disabled for containerized runs.
- If a non-container local fallback mode is still desired later, `webServer` can remain available behind an env switch, but container mode should explicitly use the external app server only.

## Implementation Scope

### 1. Add A Production-Oriented Dockerfile
- Create a repo `Dockerfile` based on `node:20-alpine`.
- Make it production-like rather than dev-like.
- Include:
  - dependency installation steps
  - build step
  - runtime package installation for the app image
  - explicit static serving command for built assets
- Do not mirror the dev container's `npm install && npm run dev` behavior.

### 2. Extend Compose To Separate Dev And Test Roles
- Keep the existing `app` service as the dev server.
- Add a Playwright service alongside it in the same `docker-compose.yml`.
- Ensure both services mount the repo consistently.
- Ensure the Playwright service can target the app service reliably.

### 3. Adjust Playwright Configuration For External Server Mode
- Update `playwright.config.ts` so containerized runs do not start `webServer`.
- Point Playwright at the dev container server instead.
- Preserve HTTPS handling if the dev server continues using Vite basic SSL.
- Keep this change minimal and focused on execution environment, not on test redesign.

### 4. Keep Existing Specs And Stabilize Execution First
- Do not redesign the current spec files in this block.
- First prove that the existing Playwright suite can run from the Debian test container against the Alpine dev container.
- Only after execution works should selector quality or coverage gaps be revisited.

### 5. Align Commands With The New Container Model
- Ensure documented test commands map cleanly to the compose-based Playwright service.
- Clarify that browser installation belongs to the Playwright container, not the Alpine app container.
- Remove assumptions that Playwright installs or launches browsers inside the app container.

## Risks
- If Playwright `webServer` is left enabled in container mode, it may create duplicate servers and port conflicts.
- Alpine app runtime and Debian Playwright runtime are intentionally different, so tests must be understood as browser-environment verification, not proof of Alpine browser support.
- The production Dockerfile may still need later runtime package refinement once actual deployment behavior is validated.
- HTTPS certificate handling may require explicit trust bypass in containerized Playwright runs.
- Compose networking details may require small config changes depending on whether host networking remains mandatory for both services.

## Verification
- `docker-compose.yml` can start the Alpine `app` dev service successfully.
- The repo `Dockerfile` builds successfully from `node:20-alpine`.
- The production image can serve built static assets with its configured static server command.
- The Playwright service can run browser tests without installing browsers in the Alpine app container.
- Playwright reaches the dev container's server and does not attempt to start its own `webServer` in container mode.
- `npm run test:short` and `npm run test:long` can be mapped cleanly to the Playwright container workflow.

## Recommended Execution Order
1. Add the production-oriented Alpine `Dockerfile`.
2. Verify the Dockerfile can build and serve the app in a production-like way.
3. Extend `docker-compose.yml` with the Playwright-only test service.
4. Update Playwright config so containerized runs use the dev container server and disable internal `webServer` startup.
5. Run existing Playwright specs from the test container against the app container.
6. Fix only environment/execution issues needed to make the container split reliable.
7. Revisit spec quality and coverage only after container execution is stable.

## Acceptance Criteria
- The repo contains a production-oriented `Dockerfile` based on `node:20-alpine`.
- Dev remains fast and convenient through the compose `app` service.
- Playwright runs in its own Debian-based container.
- The Playwright container starts no app server and no extra helper service.
- The only web server used during containerized tests is the one started by the dev `app` container.
- Playwright `webServer` is disabled for containerized test execution.
