# Kind Island - Follow-up Code Quality Improvement Plan

## Goal
Improve code quality in the gallery/viewer area after Happy Tiger without changing supported behavior, weakening type safety, or introducing broad abstractions that a weak executor could only partially integrate.

This plan assumes the executor is error-prone, may over-refactor, and may confuse cleanup with redesign. The plan therefore uses:
- small isolated blocks
- explicit file boundaries
- exact pre-checks before edits
- exact validation after each block
- strong stop conditions
- a bias toward local simplification over reusable abstractions

## Why This Plan Exists
Happy Tiger correctly stopped after the minimum safe quality win. The following issues remain and are worth addressing:
- `GalleryGrid.svelte` still has 5 repetitive focus-trap reactive blocks
- keyboard navigation guard is still too narrow and may hijack interactive descendants
- `ViewerWrapper.svelte` still contains repeated unsafe PhotoSwipe content/item casts
- image replacement in `ViewerWrapper.svelte` still uses direct `image.onload` assignment, which is fragile in a hot path
- `bulk-actions.ts` still repeats policy/guard patterns enough to justify one small cleanup

## Scope
In scope:
- `src/components/gallery/GalleryGrid.svelte`
- `src/components/gallery/utils/keyboard-navigation.ts`
- `src/components/gallery/ViewerWrapper.svelte`
- `src/components/gallery/utils/bulk-actions.ts`
- `src/components/gallery/utils/viewer-types.ts` only if required by a block
- `src/components/gallery/utils/object-url-lifecycle.ts` only if required by a block
- `STATUS.md`

Out of scope:
- feature changes
- routing changes
- Telegram adapter changes
- visual redesign
- CSS architecture changes
- PhotoSwipe behavior redesign
- new test framework setup
- moving large DOM-rendering viewer logic into a new abstraction layer
- broad utility extraction outside the gallery/viewer area

## Non-Negotiable Rules For The Executor

### Rule A. Prefer local simplification over shared abstractions
If logic is duplicated only inside one file, keep the fix inside that file unless at least 2 active files need the same helper.

### Rule B. Do not mix behavior changes with structural cleanup
Each block must do one kind of work only:
- duplication reduction
- guard hardening
- cast centralization
- event-handling hardening
- tiny policy extraction

Do not combine blocks just because they touch the same file.

### Rule C. Preserve runtime behavior unless a block explicitly fixes a safety bug
If behavior is ambiguous, preserve current working behavior and record uncertainty in `STATUS.md` rather than guessing.

### Rule D. No broad “cleanup while here” edits
If a block touches `ViewerWrapper.svelte`, only edit the exact area named by that block.

### Rule E. Keep all viewer lifecycle ownership in `ViewerWrapper.svelte`
Do not move viewer open/close, route sync, or PhotoSwipe ownership into utilities in this plan.

### Rule F. Validation is mandatory after every code block
After each logical block:
1. run Docker type check
2. run required short Playwright validation
3. run long Playwright validation when the block touches `GalleryGrid.svelte` or `ViewerWrapper.svelte`
4. update `STATUS.md`
5. commit before starting the next block

### Rule G. Stop if confidence drops
Stop and do not continue to the next block if:
- type check fails and the cause is not obviously local
- short tests fail and the failure is plausibly related
- long tests fail and the failure is plausibly related
- the executor cannot explain why behavior remains equivalent in 1-2 sentences
- a proposed helper needs more than one callback plus external mutable state to work

## Recommended Execution Order
Use this order exactly:
1. simplify `GalleryGrid` focus-trap setup
2. harden keyboard navigation guard
3. centralize PhotoSwipe content/item casts in `ViewerWrapper`
4. harden image replacement event handling in `ViewerWrapper`
5. simplify duplicated guard policy in `bulk-actions.ts`
6. optional final polish only if all earlier blocks pass cleanly

Reason for this order:
- Blocks 1 and 2 are lower-risk maintainability/safety work
- Block 3 reduces type/cast noise before touching hot-path image logic
- Block 4 is riskier and should happen only after earlier cleanup is stable
- Block 5 is optional and should stay small

## Block 1 - Simplify Gallery Focus-Trap Setup

### Goal
Remove the 5-block repeated focus-trap reactive pattern in `GalleryGrid.svelte` without changing panel visibility, escape behavior, or which panel receives focus.

### Files
- `src/components/gallery/GalleryGrid.svelte`
- `STATUS.md`

### Read-before-edit checklist
Before editing, inspect and understand:
- the 5 panel element bindings
- the 5 active-state stores
- the shared `cleanupFocusTraps` array
- the existing cleanup-on-no-active-panels block
- the `onDestroy` cleanup block

### Preferred implementation
Use one tiny local helper and keep it inside `GalleryGrid.svelte`.

Recommended shape:
- add a local helper like `activatePanelFocusTrap(active, element, onEscape)`
- helper must:
  - clear `cleanupFocusTraps`
  - do nothing when inactive or element is null
  - install one `trapFocus(...)`
  - push exactly one cleanup function when active
- keep the helper in the same component file
- replace the 5 duplicated reactive blocks with either:
  - 5 one-line reactive calls to the helper, or
  - one config array and one reactive block if that stays simple

### Strong constraints
Do not:
- extract this into a new utility file
- change panel markup
- change cancel callbacks
- change when no-panel cleanup runs
- change `trapFocus` options

### Acceptance criteria
- no duplicated 5-block focus-trap pattern remains
- `cancelDownloads`, `cancelForwards`, `cancelShares`, `cancelCopies`, `cancelUploadQueue` still map correctly
- only one trap is active at a time
- cleanup still runs when no panels are active
- cleanup still runs on destroy
- type check passes
- short suite passes
- long suite passes

### Commit message
`refactor: simplify gallery progress panel focus traps`

## Block 2 - Harden Keyboard Navigation Guard

### Goal
Prevent gallery keyboard navigation from hijacking input inside more interactive descendants.

### Files
- `src/components/gallery/utils/keyboard-navigation.ts`
- `STATUS.md`

### Read-before-edit checklist
Before editing, inspect and understand:
- current `event.target` guard
- all keys that call `preventDefault()`
- where `handleGalleryKeyDown()` is used in `GalleryGrid.svelte`

### Preferred implementation
Add one small local predicate in `keyboard-navigation.ts`.

Recommended minimum safe version:
- create helper such as `isTextEntryTarget(target: EventTarget | null): boolean`
- return true when target is an `HTMLElement` that is:
  - `HTMLInputElement`
  - `HTMLTextAreaElement`
  - `HTMLSelectElement`
  - `isContentEditable === true`
- call this helper before any `preventDefault()` logic

### Optional extension
If the DOM already contains text-editing ARIA roles, handle them only if clearly present in the codebase. Do not invent speculative role lists.

### Strong constraints
Do not:
- change arrow navigation math
n- change selection semantics
- change Escape behavior
- change scroll behavior
- add global document listeners

### Acceptance criteria
- keyboard navigation still works in grid and list views
- inputs, textareas, selects, and contenteditable targets are not hijacked
- `preventDefault()` is not called for those targets
- type check passes
- short suite passes
- long suite passes

### Commit message
`fix: narrow gallery keyboard handling scope`

## Block 3 - Centralize Viewer PhotoSwipe Casts

### Goal
Reduce duplicated unsafe casts in `ViewerWrapper.svelte` by centralizing PhotoSwipe content/item extraction behind tiny local helpers.

### Files
- `src/components/gallery/ViewerWrapper.svelte`
- `src/components/gallery/utils/viewer-types.ts` only if strictly needed
- `STATUS.md`

### Why this block matters
Current code still repeats assertions such as:
- `zoomLevelObject.itemData.item as MediaItem | undefined`
- `(content.data as { item?: MediaItem } | undefined)?.item`
- `event.content as ViewerContent`

A weak executor is likely to miss one of these later. This block reduces drift by moving them behind one narrow point.

### Preferred implementation
Keep all helpers local to `ViewerWrapper.svelte` unless at least 2 files need them.

Recommended shape:
- add local helper `getViewerContentItem(content: { data?: { item?: MediaItem } } | null | undefined): MediaItem | null`
- add local helper `toViewerContent(content: unknown): ViewerContent | null` only if necessary
- use those helpers at:
  - `maxZoomLevel`
  - `isContentZoomable`
  - `contentLoad`
  - `contentDestroy`

### Strong constraints
Do not:
- create a new generic PhotoSwipe adapter layer
- move PhotoSwipe event binding out of `ViewerWrapper.svelte`
- widen `ViewerContent` with catch-all index signatures unless type check forces it and the reason is recorded in `STATUS.md`
- introduce `any`

### Acceptance criteria
- repeated PhotoSwipe content/item assertions are reduced to one narrow point per kind of access
- no new type assertions are added elsewhere in the file
- behavior stays unchanged
- type check passes
- short suite passes
- long suite passes

### Commit message
`refactor: centralize viewer content type narrowing`

## Block 4 - Harden Image Replacement Event Handling

### Goal
Make the image preview-to-full replacement path safer without changing user-visible behavior.

### Files
- `src/components/gallery/ViewerWrapper.svelte`
- `STATUS.md`

### Why this block matters
Current `replaceImageSource()` still directly assigns `image.onload`. That is fragile because:
- it overwrites existing handlers
- it has no explicit stale-load guard
- it has no explicit error cleanup path

### Required read-before-edit checklist
The executor must compare and understand all of:
- `updateImageDimensions()`
- current `replaceImageSource()`
- preview image load path in `handleContentLoad()`
- `contentDestroy` URL cleanup path

### Preferred implementation
Use a minimal local hardening only.

Recommended shape:
- replace direct `image.onload = ...` assignment in `replaceImageSource()` with one-shot event listeners
- use one small nested helper for attaching the full-image load handler if needed
- ensure preview URL revocation still happens only after full image successfully loads when `revokePreviewOnLoad` is true
- if adding error handling, keep it minimal:
  - do not revoke the new full URL just because load failed unless current behavior clearly requires it
  - do not change placeholder behavior
- optionally guard handler effects by checking the image still points at the same `fullUrl`

### Strong constraints
Do not:
- rewrite `handleContentLoad()`
- change preview-first behavior
- change progress handling
- change URL ownership outside `replaceImageSource()`
- change viewer close or route behavior

### Acceptance criteria
- preview-to-full replacement still works
- dimensions still update after full image load
- previous full URL is still revoked when replaced
- preview URL is still revoked at the correct time
- no extra double-revocation path is introduced
- type check passes
- short suite passes
- long suite passes

### Commit message
`fix: harden viewer image replacement listeners`

## Validation Protocol
Use this protocol after every completed block.

### Required commands
1. Type check
   `docker run --rm --network host -v "$(pwd)":/app -w /app node:24-alpine npm run check`

2. Short suite
   `docker-compose -f docker-compose.test.yml up --build playwright`

3. Long suite
   `docker-compose -f docker-compose.test.yml run --rm playwright npx playwright test --config=playwright.config.ts --grep "@long" --project=desktop-chrome --reporter=line`

### Long-suite decision rules
- Run the long suite after Blocks 1-4 because they touch `GalleryGrid.svelte` or `ViewerWrapper.svelte`
- Block 5 can skip long validation if only `bulk-actions.ts` changes and no UI wiring changes
- If long validation fails on an unrelated flaky test, rerun once after resetting the compose stack, then record both results in `STATUS.md`
