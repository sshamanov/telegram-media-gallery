# Silent Knight - Code Quality Improvement Plan

## Goal
Improve code quality in the recently refactored gallery/viewer area by correcting the highest-risk refactor regression, finishing partially applied safety cleanup, and tightening local helper design without changing accepted product behavior.

This plan is intentionally narrow:
- fix concrete quality issues found in the latest refactor work
- preserve current supported gallery/viewer behavior from `APPLICATION_SPEC.md`
- avoid speculative architecture work
- prefer local simplification over new shared abstractions

## Why This Plan Exists
A review of the recent Kind Island follow-up found that the overall direction was good, but several issues remain:
- `GalleryGrid.svelte` focus-trap setup is likely logically wrong and can clear the active trap from a later inactive reactive block
- `ViewerWrapper.svelte` still uses direct `image.onload` assignment in the preview path, so image-load handling is inconsistent
- PhotoSwipe type narrowing was centralized, but safety is still mostly assertion-based rather than clearly bounded
- the new viewer load-listener hardening does not yet explicitly manage stale listener lifecycle
- `bulk-actions.ts` is cleaner, but the tiny helper extraction can be made clearer without broadening scope
- formatting/indentation in touched blocks regressed and should be normalized only in locally touched regions

## Scope
In scope:
- `src/components/gallery/GalleryGrid.svelte`
- `src/components/gallery/ViewerWrapper.svelte`
- `src/components/gallery/utils/keyboard-navigation.ts` only if a follow-up is needed after focused review
- `src/components/gallery/utils/bulk-actions.ts`
- `STATUS.md`

Out of scope:
- architecture redesign
- new shared utility layers outside the gallery/viewer area
- routing changes
- adapter changes
- CSS redesign
- new test framework setup
- unrelated formatting churn

## Non-Negotiable Rules
1. Preserve supported behavior from `APPLICATION_SPEC.md`; this is a quality/safety plan, not a feature plan.
2. Fix the likely `GalleryGrid` regression first before touching lower-risk cleanup.
3. Keep viewer lifecycle ownership in `ViewerWrapper.svelte`.
4. Prefer local helpers over new files unless at least two active files genuinely need the same abstraction.
5. After each code block:
   - run Docker type check
   - run short Playwright suite
   - run long Playwright suite when touching `GalleryGrid.svelte` or `ViewerWrapper.svelte`
   - update `STATUS.md`
   - commit before moving on
6. If a validation failure is plausibly related, stop and diagnose before continuing.

## Execution Order
Use this order exactly:
1. Fix `GalleryGrid` focus-trap regression risk
2. Unify viewer preview/full image load handling
3. Tighten viewer listener lifecycle and local narrowing clarity
4. Reassess `bulk-actions.ts` helper shape and perform minimal cleanup
5. Optional local formatting normalization only in touched regions

Reason for this order:
- Block 1 addresses the only likely real behavioral regression found in review
- Blocks 2 and 3 finish the partially applied viewer safety work while context is warm
- Block 4 is low risk and should stay small
- Block 5 only happens if directly justified by earlier edits

## Block 1 - Fix Gallery Focus-Trap Regression Risk

### Goal
Ensure that exactly one active progress panel trap remains installed when a panel is active, and that inactive reactive paths do not clear a trap installed by an active panel.

### Files
- `src/components/gallery/GalleryGrid.svelte`
- `STATUS.md`

### Current problem
The current `activatePanelFocusTrap(active, element, onEscape)` helper clears `cleanupFocusTraps` on every call. Because five reactive calls run independently, an inactive call can clear the trap installed by the active one.

### Preferred implementation
Replace the five independent reactive helper calls with one reactive selection of the active panel configuration.

Recommended shape:
- keep `cleanupFocusTraps` ownership in `GalleryGrid.svelte`
- compute one local `activePanelConfig` from the queue states in priority order
- use one reactive block to:
  - clear existing traps
  - install a single trap only when `activePanelConfig` and its bound element exist
- keep the existing no-active cleanup and `onDestroy` cleanup only if still necessary after simplification; remove redundant cleanup if a single reactive block fully owns setup/teardown

### Strong constraints
Do not:
- move focus-trap logic into a new utility file
- change panel markup
- change escape callbacks
- change trap options
- introduce a generalized registry abstraction

### Acceptance criteria
- active panel focus is trapped reliably
- inactive reactive paths cannot clear an active trap
- only one trap is active at a time
- destroy cleanup still works
- type check passes
- short suite passes
- long suite passes

### Commit message
`fix: restore gallery progress panel focus trapping`

## Block 2 - Unify Viewer Image Load Handling

### Goal
Make the image preview path and full-image replacement path use one consistent event-listener strategy instead of mixing direct `onload` assignment and one-shot listeners.

### Files
- `src/components/gallery/ViewerWrapper.svelte`
- `STATUS.md`

### Current problem
`replaceImageSource()` now uses one-shot listeners, but the preview load path still assigns `image.onload` directly before `image.src = previewUrl`.

### Preferred implementation
Create one local helper for image load listener attachment and use it in both places.

Recommended shape:
- extract the nested listener-attachment logic out of `replaceImageSource()` into one file-local helper
- use that same helper for the preview image path in `handleContentLoad()`
- preserve current behavior:
  - preview loads first when available
  - dimensions update after preview/full image load
  - preview URL revocation still occurs only after successful full-image load when requested

### Strong constraints
Do not:
- rewrite `handleContentLoad()` broadly
- change preview-first behavior
- change load-progress behavior
- change URL ownership beyond what is required for listener consistency

### Acceptance criteria
- no direct `image.onload = ...` remains in the touched image flow
- preview and full replacement use the same local listener strategy
- dimensions still update correctly
- type check passes
- short suite passes
- long suite passes

### Commit message
`refactor: unify viewer image load handling`

## Block 3 - Tighten Viewer Listener Lifecycle And Local Narrowing

### Goal
Reduce residual fragility in `ViewerWrapper.svelte` by making listener lifecycle clearer and replacing broad assertion helpers with narrower local contracts where feasible.

### Files
- `src/components/gallery/ViewerWrapper.svelte`
- `STATUS.md`

### Current problem
- one-shot listeners are safer than `onload`, but stale pending listeners are not explicitly tracked/cleared
- `getViewerContentItem`, `getSlideDataItem`, and `toViewerContent` centralize assertions but still rely on broad internal casts

### Preferred implementation
Make the smallest safe improvement that increases clarity without inventing a PhotoSwipe abstraction layer.

Recommended shape:
- add one local mechanism to clear/replace pending image listeners before attaching a new one when reusing the same `img` element
- tighten helper names or signatures so each helper reflects the actual shape it handles
- where possible, narrow from `unknown` to small local structural types instead of broad `ViewerContent` assertion first
- keep all logic in `ViewerWrapper.svelte`

### Strong constraints
Do not:
- create a generic PhotoSwipe wrapper layer
- move event binding out of `ViewerWrapper.svelte`
- widen types with catch-all index signatures
- introduce `any`

### Acceptance criteria
- stale image listener behavior is explicitly managed
- local narrowing helpers are clearer and no broader than necessary
- behavior remains unchanged
- type check passes
- short suite passes
- long suite passes

### Commit message
`refactor: tighten viewer event and content guards`

## Block 4 - Minimal Bulk Action Helper Cleanup

### Goal
Make `bulk-actions.ts` slightly clearer by keeping only helper extraction that genuinely improves readability.

### Files
- `src/components/gallery/utils/bulk-actions.ts`
- `STATUS.md`

### Current problem
`hasSelection()` is clearly fine. `createOfflineWarningToast()` is acceptable but only mildly useful because each action still provides distinct text and still wraps `pushToast(...)` at each callsite.

### Preferred implementation
Choose the smaller of these two options after reading the file carefully:
- keep `createOfflineWarningToast()` if it reads clearly and remains the smallest truthful abstraction, or
- replace it with a slightly stronger local helper such as `pushOfflineWarning(pushToast, text)` if that makes call sites cleaner without hiding side effects

### Decision rule
Do this block only if the result is clearly simpler than the current version. If not, explicitly defer it.

### Strong constraints
Do not:
- create generic action executors
- move handler side effects into a shared workflow helper
- change toast copy
- touch `GalleryGrid.svelte` wiring for this block

### Acceptance criteria
- helper shape is at least as readable as current code
- side effects remain obvious at call sites
- behavior remains unchanged
- type check passes
- short suite passes
- long suite may be skipped if only `bulk-actions.ts` changes

### Commit message
`refactor: clarify bulk action toast guards`

## Validation Protocol
After each completed block:
1. Type check
   `docker run --rm --network host -v "$(pwd)":/app -w /app node:24-alpine npm run check`
2. Short suite
   `docker-compose -f docker-compose.test.yml up --build playwright`
3. Long suite for Blocks 1-3
   `docker-compose -f docker-compose.test.yml run --rm playwright npx playwright test --config=playwright.config.ts --grep "@long" --project=desktop-chrome --reporter=line`

Long-suite rule for Block 4:
- skip long suite if only `bulk-actions.ts` changes and no gallery/viewer wiring changes are made

If a long test flakes:
- rerun the failing test once
- record both results in `STATUS.md`
- only continue if the failure is confidently unrelated/flaky
