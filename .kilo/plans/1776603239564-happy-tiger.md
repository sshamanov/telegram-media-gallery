# Happy Tiger - Code Quality Hardening Plan

## Goal
Improve code quality in the recently refactored gallery/viewer area without introducing behavior drift, speculative abstraction, or partial cleanups that leave the codebase in a more confusing state.

This plan is written for a relatively weak executor. It assumes the executor may over-refactor, miss subtle behavior coupling, or stop after a local improvement without checking for broader consistency. The plan therefore uses:
- small isolated blocks
- explicit file boundaries
- exact success criteria
- rollback/stop conditions
- mandatory validation after each logical block
- a bias toward deletion and consolidation over new abstractions

## Scope
In scope:
- `src/components/gallery/ViewerWrapper.svelte`
- `src/components/gallery/GalleryGrid.svelte`
- `src/components/gallery/utils/object-url-lifecycle.ts`
- `src/components/gallery/utils/photoswipe-integration.ts`
- `src/components/gallery/utils/video-player.ts`
- `src/components/gallery/utils/keyboard-navigation.ts`
- `src/components/gallery/utils/bulk-actions.ts`
- optional new shared type file under `src/components/gallery/utils/` only if needed by this plan
- `STATUS.md`

Out of scope:
- unrelated product features
- Telegram adapter changes
- CSS redesign
- test framework setup beyond existing required validation
- broad component rewrites
- converting large imperative DOM-rendering viewer code into a new framework abstraction

## Quality Findings Being Addressed

### Q1. `replaceImageSource()` extraction likely weakened viewer correctness
Current risk:
- extracted helper no longer updates image dimensions after full image load
- extracted helper no longer revokes a previous full URL if the image source is replaced again
- this creates correctness risk in PhotoSwipe sizing and object URL lifecycle

### Q2. Dead/unintegrated utility exports remain after refactor
Current risk:
- `photoswipe-integration.ts` exports helpers not used anywhere
- `video-player.ts` exports helpers not used anywhere
- `object-url-lifecycle.ts` exports URL helpers not used anywhere
- this creates misleading API surface and maintenance noise

### Q3. `console.warn` remains in production code
Current risk:
- violates project rule banning direct console usage
- creates inconsistent logging behavior

### Q4. `ViewerContent` shape is duplicated in multiple places
Current risk:
- easy drift between copies
- future edits likely to miss one copy

### Q5. `GalleryGrid.svelte` still contains repetitive focus-trap reactive blocks
Current risk:
- hard to maintain
- high copy/paste risk for future edits
- subtle inconsistency risk between panels

### Q6. keyboard navigation guard is too narrow
Current risk:
- arrow/space handling may still interfere with more interactive elements than intended

### Q7. `bulk-actions.ts` mixes policy and browser side effects
Current risk:
- harder to reason about
- harder to test later
- easier to accidentally duplicate action gating logic in UI

## Strategy
Use the following implementation order exactly:
1. Fix correctness risk first (`replaceImageSource`)
2. Remove rule violations (`console.warn`)
3. Prune dead code instead of trying to “complete” abandoned abstractions
4. Consolidate duplicated types only after dead code is removed
5. Perform one small maintainability refactor in `GalleryGrid`
6. Perform one small safety refactor in keyboard navigation
7. Only improve `bulk-actions.ts` if still clearly beneficial after earlier cleanup

Do not reorder unless blocked. The first four blocks give the highest quality gain with the lowest drift risk.

## Global Execution Rules
These rules apply to every block.

### Rule A. Prefer deletion over new abstraction
If a helper is unused and not clearly better than local code, delete it instead of integrating it.

### Rule B. Do not refactor behavior and structure in the same step
Each block should do one kind of change:
- correctness fix
- deletion/pruning
- type consolidation
- duplication reduction

Avoid mixed-purpose edits.

### Rule C. Preserve existing runtime behavior unless the block explicitly fixes a bug
If behavior seems ambiguous, preserve the current working behavior and record uncertainty in `STATUS.md`.

### Rule D. Do not invent new generic helpers unless the same logic is already duplicated in at least 2 active call sites
This is critical for a weaker executor. New helpers increase drift risk.

### Rule E. Validation is mandatory after every block that changes code
After each logical block:
- run `npm run check` in Docker
- run required short Playwright validation in dedicated test compose flow if product behavior changed or runtime code changed
- update `STATUS.md` before commit
- commit before starting the next block

### Rule F. Stop conditions
Stop and do not continue to the next block if:
- type check fails and the failure is not obviously local
- short test suite fails and the failure is plausibly related
- the executor cannot explain behavior equivalence in 1-2 sentences
- a supposedly unused helper turns out to be used outside the gallery/viewer area

## Block 1 - Restore `replaceImageSource` correctness

### Goal
Make the `replaceImageSource()` path correct again without broad viewer refactoring.

### Files
- `src/components/gallery/utils/object-url-lifecycle.ts`
- `src/components/gallery/ViewerWrapper.svelte`

### Required read-before-edit checklist
The executor must compare:
- current `replaceImageSource()` implementation
- current `updateImageDimensions()` logic in `ViewerWrapper.svelte`
- the current image preview-to-full load flow inside `handleContentLoad()`

### Preferred implementation
Use the smallest correct option:
- either move the missing behavior back into `replaceImageSource()`
- or delete the extracted helper and restore a local `replaceImageSource()` in `ViewerWrapper.svelte`

Recommended choice for a weak executor:
- restore the helper’s original behavior in the utility only if the utility can accept a small callback or enough context without widening types awkwardly
- otherwise move `replaceImageSource()` back into `ViewerWrapper.svelte` and keep `object-url-lifecycle.ts` limited to `revokeUrls()`

### Strong recommendation
For a weak executor, the safest path is likely:
1. move `replaceImageSource()` back into `ViewerWrapper.svelte`
2. delete the exported helper from `object-url-lifecycle.ts`
3. keep `revokeUrls()` in the utility

Reason:
- `replaceImageSource()` is tightly coupled to `updateImageDimensions()` and viewer-specific load behavior
- keeping it local reduces cross-file coupling and future drift

### Acceptance criteria
- full image replacement still works after preview load
- image dimensions update after the full image loads
- preview URL is revoked when appropriate
- any previous full URL is not leaked when replaced
- type check passes
- short suite passes

### Not allowed
- rewriting `handleContentLoad()` as part of this block
- introducing a new generic image loader abstraction
- changing viewer routing/close behavior

## Block 4 - Consolidate duplicated `ViewerContent` type

### Goal

### Files
- `src/components/gallery/ViewerWrapper.svelte`
- remaining viewer utility files that still use the type

### Decision rule
Only do this block if Block 3 leaves at least 2 active files using the same shape.

- keep the type local in `ViewerWrapper.svelte`

### Acceptance criteria

- no duplicate type copies remain in active code paths
- type check passes
- short suite passes

### Not allowed

## Block 5 - Reduce repetitive focus-trap logic in `GalleryGrid`

### Goal
Remove obvious duplication without changing behavior.

### File
- `src/components/gallery/GalleryGrid.svelte`

### Current target area
Reactive blocks handling:
- `downloadPanelElement`
- `forwardPanelElement`
- `sharePanelElement`
- `copyPanelElement`
- `uploadPanelElement`

### Preferred implementation
Use a tiny internal helper or a small config array in the component to centralize repeated focus-trap setup.

Recommended shape:
- one helper that accepts `(active, element, onEscape)`
- helper clears previous traps and returns a cleanup function
- component remains in one file

Alternative acceptable shape:
- one derived list of panel configs and a single reactive block

### Strong constraint
Do not extract this into another new utility file unless duplication remains substantial after simplification. For a weak executor, keeping this local is safer.

### Acceptance criteria
- panel focus-trap behavior remains identical
- all existing cancel callbacks still map correctly
- no duplicated 5-block pattern remains
- type check passes
- short suite passes

### Not allowed
- changing panel DOM structure
- changing escape behavior
- changing progress panel visibility logic

## Block 6 - Harden keyboard navigation guard

### Goal
Reduce the chance that gallery keyboard navigation hijacks input from interactive descendants.

### File
- `src/components/gallery/utils/keyboard-navigation.ts`

### Preferred implementation
Replace the narrow input check with a helper that returns true for:
- `HTMLInputElement`
- `HTMLTextAreaElement`
- `HTMLSelectElement`
- elements with `contenteditable`
- possibly elements with interactive ARIA/text-editing roles if already represented in DOM

Recommended minimum safe version:
- check `event.target instanceof HTMLElement`
- skip handling if target is form control or `isContentEditable`

### Acceptance criteria
- keyboard navigation still works in gallery grid/list
- inputs and text-editable contexts are not hijacked
- type check passes
- short suite passes

## Validation Protocol
Use this protocol after each completed block.

### Required commands
1. Type check:
   `docker run --rm --network host -v "$(pwd)":/app -w /app node:24-alpine npm run check`
2. Short suite:
   `docker-compose -f docker-compose.test.yml up --build playwright`

### Validation notes for weak executor
- If short suite fails with Vite overlay or container residue, first reset the compose stack and rerun once.
- Do not assume unrelated failure unless the rerun proves it.
- Record both the failure and the rerun result in `STATUS.md` truthfully.

## Commit Plan
Commit after each logical block. Do not batch multiple blocks.

Recommended commit sequence:
1. `fix: restore viewer image replacement behavior`
2. `chore: replace gallery console logging with debug helpers`
3. `refactor: prune unused gallery utility exports`
4. `refactor: consolidate viewer content typing` (only if Block 4 is needed)
5. `refactor: simplify gallery focus trap setup`
6. `fix: narrow gallery keyboard handling scope`
7. `refactor: simplify bulk action guards` (optional, only if executed)

## STATUS.md Requirements
For each block, update:
- Current Todo States
- Plan And Todo History
- Last Validation
- Recent Commit Log
- Next Execution Order

If a block is skipped by design, record it explicitly as skipped/deferred with reason.

## Executor Checklist
Before editing a block, the executor must confirm all of the following:
- I know exactly which files are in scope for this block.
- I am not introducing a new abstraction unless it already serves at least 2 active callers.
- I am not changing behavior outside the stated goal.
- I will run both required validations after this block.
- I will update `STATUS.md` before committing.
- I will stop if validation fails and the cause is unclear.

## Recommended End State
A successful implementation should end with:
- viewer image replacement logic restored and trustworthy
- no direct `console.*` usage in gallery utils
- no dead post-refactor exports left behind
- no duplicated active `ViewerContent` type definitions
- simpler, less repetitive focus-trap setup in `GalleryGrid`
- safer keyboard event gating
- optional `bulk-actions.ts` cleanup only if clearly beneficial

## Minimum Acceptable End State
If time or confidence is limited, Blocks 1 through 4 alone are still a strong quality improvement and should be preferred over attempting all seven blocks poorly.

That minimum path is the best quality/safety tradeoff for a weaker executor.
