# Node 24 Runtime Migration Plan

## Goal
- Move the project’s documented and containerized runtime baseline from `node:20-alpine` to `node:24-alpine`.
- Verify that the current Svelte/Vite/Playwright workflow remains compatible on Node 24.
- Keep the manual app compose path and the dedicated test compose path aligned on the same Node major unless validation proves a temporary split is necessary.

## Current Findings
- The repo does not currently declare a required Node version in `package.json`; there is no `engines` field.
- The project operational baseline is defined by docs and containers, not package metadata.
- Current runtime references to `node:20-alpine` are present in:
  - `docker-compose.yml`
  - `docker-compose.test.yml`
  - `AGENTS.md`
  - `APPLICATION_SPEC.md`
  - `TESTING_STRATEGY.md`
  - historical command examples in `.kilo/status.md`
- Existing validation history in `.kilo/status.md` is recorded with Node 20 commands; those entries are historical facts and should not be rewritten retroactively.
- `package.json` dependencies do not show an obvious hard lock to Node 20, but compatibility still needs to be validated empirically.

## Scope

### In Scope
- Update runtime container references from `node:20-alpine` to `node:24-alpine`.
- Add explicit package metadata if desired (`engines.node`) to make the new baseline visible.
- Re-run required validation on Node 24 and record the results in `.kilo/status.md`.
- Update governing documentation so the runtime baseline is consistently described.

### Out Of Scope
- Dependency upgrades unrelated to Node 24 compatibility.
- Playwright browser image major changes unless required by validation.
- Unrelated auth, gallery, accessibility, or feature work.

## Implementation Plan

### 1. Establish the new baseline explicitly
- Update runtime references in:
  - `docker-compose.yml`
  - `docker-compose.test.yml`
  - `AGENTS.md`
  - `APPLICATION_SPEC.md`
  - `TESTING_STRATEGY.md`
- Decide whether to add `package.json` metadata such as:
  - `"engines": { "node": ">=24 <25" }`
  - optional package-manager enforcement only if the repo already uses such constraints consistently.
- Do **not** rewrite historical validation records in `.kilo/status.md`; instead, add new Node 24 validation entries.

### 2. Validate Node 24 compatibility in the real project workflow
- Run type check in Docker with `node:24-alpine`:
  - `docker run --rm --network host -v "$(pwd)":/app -w /app node:24-alpine npm run check`
- Run build in Docker with `node:24-alpine` because runtime migration affects the toolchain surface:
  - `docker run --rm --network host -v "$(pwd)":/app -w /app node:24-alpine npm run build`
- Run the required short Playwright suite through the dedicated compose workflow after switching the app container to Node 24:
  - `docker-compose -f docker-compose.test.yml run --rm playwright npx playwright test --config=playwright.config.ts --grep "@short" --project=desktop-chrome`
- If auth or other advanced flows are part of the touched runtime-sensitive surface, consider the relevant long/smoke subset only if current spec/status require it.

### 3. Handle compatibility failures with minimal fallback policy
- If Node 24 fails due to Alpine/native/runtime incompatibility:
  - record the exact failure in `.kilo/status.md`
  - identify whether the issue is in dependencies, Docker image choice, or project scripts
  - prefer a targeted fix over reverting immediately
- If a temporary split becomes necessary, use this order of preference:
  1. keep both manual and test app containers on Node 24
  2. if blocked, temporarily keep Playwright app service on Node 20 while manual app moves to 24, but document it clearly as transitional
  3. remove the split once compatibility is restored
- Only keep Node 20 if Node 24 validation shows a real blocker that cannot be resolved in the same logical block.

### 4. Update status and commit as one runtime/tooling block
- Register the Node 24 migration work in `.kilo/status.md` before execution.
- Record todo state changes and each validation command/result.
- Commit with a conventional message such as:
  - `chore: migrate runtime baseline to node 24`

## Files Likely To Change
- `docker-compose.yml`
- `docker-compose.test.yml`
- `package.json` (optional `engines` field)
- `AGENTS.md`
- `APPLICATION_SPEC.md`
- `TESTING_STRATEGY.md`
- `.kilo/status.md`

## Risks
- Some tooling may behave differently on Node 24 even without explicit version constraints.
- Alpine-based images can surface compatibility differences not obvious from package metadata.
- Adding an `engines` field may affect contributors if their local environment differs from the new baseline.

## Acceptance Criteria
- Runtime references use `node:24-alpine` consistently where the active project baseline is defined.
- Required validation passes on Node 24 and is recorded in `.kilo/status.md`.
- Manual compose and dedicated test compose remain clearly separated by purpose.
- Documentation reflects Node 24 as the current runtime baseline without rewriting historical Node 20 validation facts.
