# UI Test Implementation Plan

## Decision
- Default to a hybrid model.
- Required short/long test gates must be real Playwright test files committed to the repo.
- MCP Playwright is a secondary tool for exploratory verification, failure triage, and reproducing flaky behavior.

## Why this is the right approach
- `AGENTS.md` requires `npm run test:short` and `npm run test:long` as repeatable gates after logical work blocks and before plan/spec milestones.
- The current `package.json` scripts point to `tests/test-runner.js`, and `tests/short-test.js` / `tests/long-test.js` only print plans and return success. They are placeholders, not tests.
- Manual MCP runs are useful, but they are not durable, reviewable, versioned assertions and cannot reliably satisfy required repo-level gates.
- Telegram Gallery already has the right shape for deterministic UI automation: mock adapter support, sample data, defined short/long scopes, and explicit desktop/mobile requirements.

## Comparison

### Real Playwright test files as primary
Pros:
- Repeatable and scriptable from `npm run test:short` / `npm run test:long`
- Versioned in git, reviewable in PRs, and enforceable in CI
- Can encode exact app expectations with assertions instead of human interpretation
- Good fit for required regression coverage of auth, dialogs, views, viewer, settings, uploads, sharing, cache flows
- Supports multiple projects/devices (desktop + mobile) with shared fixtures

Cons:
- Requires setup and maintenance
- Selectors/fixtures must be kept in sync with UI changes
- Initial work is larger than ad hoc manual checking

### MCP Playwright manual-flow execution as primary
Pros:
- Fast for exploration and debugging
- Useful for interactive investigation when a scripted test fails
- Good for checking visual state and reproducing issues in context

Cons:
- Not suitable as a required gate for every logical block/commit
- Not versioned as executable assertions in the repo
- Harder to keep consistent across agents and over time
- Easy to drift from defined short/long scope and acceptance criteria

## Final policy
- Primary: repo-owned Playwright spec files behind `test:short` and `test:long`
- Secondary: MCP Playwright smoke/debug checklist for diagnosis only
- The current placeholder JS plan-printers must be removed from the required path and replaced with real assertions

## Implementation scope

### 1. Replace placeholder test commands with real Playwright execution
- Remove the current fake success path in:
  - `tests/test-runner.js`
  - `tests/short-test.js`
  - `tests/long-test.js`
- Introduce real Playwright setup, for example:
  - `playwright.config.ts`
  - `tests/e2e/short/*.spec.ts`
  - `tests/e2e/long/*.spec.ts`
  - shared helpers/fixtures for mock login and navigation
- Update `package.json` so:
  - `test:short` runs only short specs
  - `test:long` runs long specs
  - `test:all` runs both

### 2. Make test environment independent from `.env`
- Do not depend on editing `.env` for UI tests.
- Configure mock mode explicitly in the test launch path instead, e.g. server command env override or Playwright webServer env.
- Ensure tests always boot the app in mock mode deterministically.
- Keep runtime mock switching out of the core automated path.

### 3. Add real short suite coverage
- Short suite must cover only the basic safe flows:
  - auth screen loads
  - phone auth mock flow
  - QR auth screen render / basic flow entry
  - post-login dialog list
  - Galleries / Groups / Chats tab transitions
  - search input behavior
  - open dialog to gallery
  - gallery grid/list transition
  - open/close fullscreen viewer
  - open/close settings
- Explicitly exclude uploads, downloads, sharing, forwarding, cache clearing, and destructive flows.
- Keep short suite runtime low enough for mandatory frequent execution.

### 4. Add real long suite coverage
- Long suite includes short coverage plus:
  - upload flows
  - download flows
  - sharing / forwarding / copy actions
  - cache management UI
  - reconnect / session-expiry / error-state flows
  - mobile viewport flows
  - higher-volume gallery loading and related stability checks
- Organize long tests by feature area so trigger-based execution maps naturally to changed logic.

### 5. Build shared fixtures and selectors
- Create stable helpers for:
  - launching the app with mock mode
  - authenticating via mock phone flow
  - navigating to dialog list / gallery / settings
  - selecting a dialog reliably from sample data
- Prefer robust role/text/test-id selectors.
- If needed, add minimal `data-testid` hooks only where accessibility selectors are insufficient.

### 6. Align sample data with deterministic assertions
- Validate and extend `samples/dialogs.json` and `samples/dialog-media/*.json` so tests can assert:
  - known dialog titles
  - known media counts/types
  - predictable gallery contents
- Ensure the mock adapter uses these fixtures consistently and falls back only outside test scenarios.

### 7. Fix gating documentation and commands
- Update `TESTING_STRATEGY.md` so it describes real Playwright-based execution, not placeholder scripts.
- Update `AGENTS.md` language to clarify:
  - short/long tests mean real automated assertions
  - MCP Playwright is not a substitute for mandatory short/long gates
  - MCP is for triage/debug after a scripted failure or for exploratory checks
- Add or update `.kilo/command/` entries if needed so Kilo commands map cleanly to the new test scripts.

### 8. Add MCP Playwright smoke/triage checklist
- Keep a small documented checklist for agents when scripted tests fail:
  - launch app manually in browser via MCP
  - verify auth screen render
  - verify mock login path
  - verify dialogs load
  - verify selected failing UI flow step-by-step
  - capture screenshot / console / network info
- This checklist supports debugging, not release gating.

### 9. Verification and acceptance criteria
- `npm run test:short` must fail on real UI regressions and pass only with real assertions.
- `npm run test:long` must exercise extended flows and fail on corresponding regressions.
- The short suite must be fast enough for required frequent execution.
- The long suite must be logically partitioned so trigger-based use remains practical.
- A full run should be executed once after implementation and all failures fixed.

## Recommended execution order
1. Replace placeholder scripts with real Playwright infrastructure
2. Wire mock mode into test launch without `.env`
3. Implement short suite first until fully green
4. Update docs/rules so repo gates point to real tests
5. Implement long suite incrementally by feature area
6. Run full test pass once and fix failures
7. Add MCP smoke checklist for debugging workflow

## Notes for implementation
- Because current repo instructions say tests are mandatory gates, leaving placeholder scripts in place is non-compliant.
- The implementation should treat the current test scripts as temporary scaffolding to be replaced, not extended.
- If HTTPS local certs complicate automation, solve that in Playwright config/webServer rather than downgrading tests to manual-only mode.
