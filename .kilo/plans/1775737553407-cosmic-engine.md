## Decisions (final reference)

| Area | Decision |
|------|----------|
| Telegram client | **mtcute** (`@mtcute/web`) — replaces GramJS |
| Auth | Phone + code + 2FA + QR login |
| Framework | **Svelte 5** + TypeScript strict |
| Build | Vite |
| TLS / SSL | Vite basic SSL for now; separate nginx in Docker Compose with persistent cert deferred to Phase 4 / deployment hardening |
| Fullscreen viewer | **PhotoSwipe v5** |
| Storage — settings / session / bookmarks | localStorage (unchanged) |
| Storage — thumbnails | IndexedDB (Phase 0–2), Cache API via SW (Phase 3) |
| Storage — full media | IndexedDB (Phase 0–2), **OPFS** (Phase 3) |
| PWA manifest | Phase 0 |
| Service worker / offline | Phase 3 |
| Offline behavior | Option 2 — cached content + offline banner |
| Media types Phase 0 | Photos + videos only |
| Media types Phase 1 | PDF, audio, all browser-renderable, per-gallery filter |
| Multi-select | Phase 2 |
| Bulk download | Phase 2 — chained individual downloads, no ZIP |
| Bulk desktop | Downloads folder (Phase 2), File System Access API folder pick (Phase 2 bonus) |
| Forward to Telegram | Phase 2 — `forwardMessages`, dialog picker, my galleries first |
| Android Share | Phase 2 — Web Share API `navigator.share({ files })` |
| Upload | Phase 0 (basic: single file), Phase 1 (send as media vs file selector), Phase 2 (bulk upload + full queue UX) |
| Views | Grid (Phase 0) + List (Phase 1) |
| List view row | 48px thumb + filename + date + size |
| Type filter | Per-gallery filter bar + global defaults in Settings |
| Dialog limit | Unlimited (paginated) |
| Scroll position | Remembered per dialog (localStorage Map) |
| Credentials | Own `api_id`/`api_hash` in `.env` |
| Theme | Dark Phase 0; CSS vars ready for light in Phase 4 |
| Target | Chrome desktop + Android Chrome. No Safari. Android 10+. |
| Dialog avatars | Yes — lazy loaded 40px circles |
| Grid layout | Uniform squares (Phase 0); masonry toggle (Phase 4) |
| Info panel | Bottom drawer — all screen sizes for now |
| Upload button | In gallery header (`[⬆ Upload]`) |
| Toast position | Bottom — all screen sizes for now |
| Accent color | Telegram blue `#0088cc` |
| Desktop layout variants | Deferred to Phase 4 (info panel side, toast top) |

```markdown
## Tech stack
   ```

### 1.5 `.kilo/command/commit.md`

**Usage:** `/commit`

Enforces commit discipline. Runs phase-check first. Refuses to commit if any criterion is ❌. Proposes a Conventional Commits message based on what changed.

```markdown

description: Check phase criteria then commit with a conventional commit message
---
Before committing, do the following in order:

STEP 1 — Phase check:
Read TECHNICAL_MIGRATION_PLAN.md, identify the active phase, check each acceptance
criterion against the current src/ files.
If any criterion is ❌ (missing), STOP. Report what is missing. Do not commit.
If all criteria are ✅ or ⚠️ (partial is acceptable mid-phase), continue.

STEP 2 — Diff summary:
Run: git diff --stat HEAD
Run: git status
Summarize what changed in plain language.

STEP 3 — Propose commit message:
Write a Conventional Commits message (type: subject, body if needed).
Types: feat | fix | refactor | style | chore | docs | test
Subject: imperative mood, max 72 chars, no period.
Body: what changed and why, not how.

STEP 4 — Execute:
Run: git add -A
Run: git commit -m "<proposed message>"
Run: git status to confirm clean working tree.

Never use --no-verify. Never amend unless the last commit was not pushed and
was made in this session.
```

**Usage:** `@mtcute-specialist implement adapter.downloadFull with progress`

```markdown
---
You are a specialist in the @mtcute/web Telegram MTProto client library for browsers.

## System rules (inherit from AGENTS.md — enforced here too)
- Never operate outside the project working directory
- Never install system tools
- Temporary files go in ./tmp/ only
- All builds via Docker with --network host

## mtcute-specific rules for this project
1. All Telegram API calls go through src/lib/telegram/adapter.ts.
   Never import @mtcute/web outside of src/lib/telegram/mtcute.ts.
2. Photos: mtcute auto-selects largest PhotoSize (max 2560px). No manual size selection.
3. Thumbnails: call photo.getThumbnail('s') to get small size, then downloadAsBuffer().
4. Full media: use downloadAsBuffer() for images; downloadAsStream() for large videos.
5. Upload: client.uploadFile(file, { progressCallback }) then sendMedia with InputMedia.auto().
6. FLOOD_WAIT small (< threshold): mtcute handles automatically, no action needed.
   FLOOD_WAIT large: catch RpcError, check is(e, 'FLOOD_WAIT_%d'), wait e.seconds, retry.
7. Dialog pagination: loop client.getDialogs({ limit: 100, offsetDate }) until empty result.
8. Batch requests: add await sleep(100) between iterations as a polite rate-limit buffer.
9. Session: use TelegramClient with StringSession. Save via client.session.save().

## What to produce
Write or modify src/lib/telegram/mtcute.ts to implement the requested adapter method(s).
The adapter interface is defined in src/lib/telegram/adapter.ts — never change the interface
signature without explicit instruction.

Reference src-reference/main.js for MVP behavior to reproduce or improve.
```

## Part 3 — Architecture

### Adapter interface (`src/lib/telegram/adapter.ts`)

The only file that imports `@mtcute/web` is `src/lib/telegram/mtcute.ts`.
Feature code imports only from `adapter.ts`.

```ts
// Phase 0 surface
export interface TelegramAdapter {
  // Auth
  sendCode(phone: string): Promise<{ phoneCodeHash: string }>
  signIn(phone: string, code: string, hash: string): Promise<'ok' | '2fa_required'>
  signIn2FA(password: string): Promise<void>
  startQRLogin(): AsyncIterable<{ token: string; expires: number }>
  reconnect(session: string): Promise<boolean>
  logout(): Promise<void>
  getSession(): string | null

  // Dialogs
  getDialogs(opts?: { limit?: number; offsetDate?: number }): Promise<Dialog[]>

  // Messages / media
  getMessages(dialogId: string, opts: { limit: number; offsetId?: number }): Promise<Message[]>
  downloadThumbnail(media: TgMedia): Promise<Uint8Array | null>
  downloadFull(media: TgMedia, onProgress?: (pct: number) => void): Promise<Uint8Array>

  // Upload (basic Phase 0)
  uploadAndSend(dialogId: string, file: File, onProgress?: (pct: number) => void): Promise<void>

  // Forward (Phase 2 — add when needed)
  forwardMessages(toId: string, fromId: string, msgIds: number[]): Promise<void>
}
```

`Dialog`, `Message`, `TgMedia`, `MediaItem` are project-local types in `src/types/telegram.ts`.
The mtcute implementation converts mtcute's types into these. Feature code never sees mtcute types.

### Svelte stores

**Dialog pagination** — replaces the 100-item cap:
```ts
async getDialogs(): Promise<Dialog[]> {
  const all: Dialog[] = []
  let offsetDate = 0
  while (true) {
    const batch = await client.getDialogs({ limit: 100, offsetDate })
    if (!batch.length) break
    all.push(...convertBatch(batch))
    offsetDate = batch.at(-1)!.lastMessage?.date ?? 0
  }

}
```

**PhotoSwipe integration** — lazy full-quality load:
```ts
// onMount in ViewerWrapper.svelte
const pswp = new PhotoSwipe({
  dataSource: items.map(i => ({ src: '', width: i.width, height: i.height })),
  index: currentIndex,
})
pswp.on('contentLoad', async (e) => {
  e.preventDefault()
  const buffer = await adapter.downloadFull(items[e.content.index].media, pct => {
    e.content.element.style.opacity = String(pct / 100)
  })
  const blob = new Blob([buffer], { type: items[e.content.index].mimeType })
  const url = URL.createObjectURL(blob)
  e.content.element.src = url
  // store url for later revocation
})
pswp.on('contentDestroy', (e) => {
  const url = storedUrls.get(e.content.index)
  if (url) URL.revokeObjectURL(url)
})
pswp.init()
```

## Part 7 — Phase 3: Storage + Offline

**Delivers:** OPFS for full media, service worker, offline mode with cached-content banner.

### OPFS structure
```
OPFS root/
  media/
    {dialogId}/
      {messageId}.{ext}    ← full images and videos
```
Thumbnails stay in IndexedDB (small, frequent random access — IndexedDB is fine for these).

### Migration
On Phase 3 first run: iterate existing IndexedDB `fullImages` store, write each blob to OPFS, delete from IndexedDB. Show progress. One-time, cannot fail silently.

### Service worker (hand-rolled, no Workbox)
- Precache: `/`, `/index.html`, hashed JS/CSS chunks
- Runtime cache strategy: Cache First for thumbnails
- Cache name versioned — old cache deleted on SW activate

### Offline behavior
`ui.ts` store tracks `isOffline`. `App.svelte` listens to `navigator.onLine` + events. Banner shown when offline. Gallery grid renders cached thumbnails from IndexedDB/Cache API. Clicking uncached full media shows inline "Not available offline" message (no error screen).

### Phase 3 user flows

**Flow: First launch after Phase 3 upgrade (OPFS migration)**

1. User opens the app after upgrading to Phase 3 build
2. Before the main UI renders, app detects `migrationNeeded` flag (absent from localStorage)
3. Migration screen shown:
   ```
   ┌─────────────────────────────────┐
   │   Upgrading storage...          │
   │   Moving cached media to new    │
   │   storage format.               │
   │                                 │
   │   ████████████░░░░░  62%        │
   │   (This happens once only)      │
   └─────────────────────────────────┘
   ```
4. Iterates IndexedDB `fullImages` store, writes each blob to OPFS, deletes from IndexedDB
5. On finish: sets `migrationDone` in localStorage, clears migration screen, loads main app
6. On error during migration: logs error, skips that entry, continues (partial migration is fine — missing items will be re-downloaded on demand)

**Flow: Using the app offline**

1. User has no internet connection (airplane, subway, etc.)
2. Opens the PWA from home screen
3. Service worker serves app shell (HTML + JS) from cache — app loads instantly
4. ⚠ Offline banner appears at top: "Offline — showing cached content"
5. Auth: auto-reconnect attempt fails silently; if session exists, proceeds to main screen with banner
6. Dialog list: shows all previously cached dialogs (from localStorage `galleryIds` and `allDialogs` snapshot)
7. Entering a gallery: grid renders with thumbnails served from Cache API (SW intercepts thumbnail requests)
8. Items without cached thumbnails show the loading spinner, which never resolves — remains as placeholder

   Tapping a photo:
   - If full media is in OPFS: PhotoSwipe opens normally, media loads from OPFS file handle
   - If not cached: PhotoSwipe opens, content slot shows:
     ```
     ┌─────────────────────┐
     │   📵                │
     │   Not available     │
     │   offline           │
     └─────────────────────┘
     ```
   - Download/Forward/Share buttons are all disabled while offline

9. Connection restored: banner disappears. Dialog list refreshes automatically. User continues seamlessly.

**Flow: Cache settings in offline context**

Settings tab shows three storage sections:
```
STORAGE
Thumbnails (IndexedDB)    3 241 items   42 MB   [Clear]
Full media (OPFS)         847 items     2.1 GB  [Clear]
App cache (SW)            14 MB                  [Clear]

Total used: 2.15 GB
```
Each [Clear] button clears only its section. Clearing thumbnails means they will be re-downloaded on next gallery open. Clearing OPFS full media means full images and videos are re-downloaded on demand. Clearing app cache triggers the service worker to re-fetch on next page load (note: this means offline mode won't work until next online visit).

**Edge cases — Phase 3**
- OPFS not available (very old Chrome build): fall back to IndexedDB for full media; no OPFS features exposed in Settings; no migration runs.
- Service worker registration fails (HTTP instead of HTTPS, or blocked by browser policy): app still works normally online; offline mode simply unavailable; no error shown to user.
- OPFS write fails mid-download (disk full): catch error, show toast "Storage full — could not cache this file", item remains uncached.
- Migration interrupted (app closed mid-migration): on next launch, migration resumes from where it left off (check which entries exist in OPFS, skip those, continue with remaining IndexedDB entries).

## 2. Credentials: do not use Telegram Desktop's public API ID

You asked if you can use Telegram Desktop's `api_id=2040, api_hash=b18441a1ff607e10a989891a5462e627`.

**Short answer: do not do this.**

- Telegram's ToS explicitly prohibits using another app's credentials.
- Telegram has revoked public client IDs in the past when they were widely misused. If that happens your app silently breaks — every user gets an `API_ID_INVALID` error with no warning.
- It does not actually solve your security concern. The SESSION STRING is what gives access to your account, not the api_id. Anyone who extracts your session from localStorage can log in as you regardless of which api_id was used. The api_id is just an app identifier.

**What actually protects credentials, in order of effort:**

| Approach | Effort | What it protects |
|---|---|---|
| `.env` file + gitignore | 2 min | Keeps api_id/hash out of the repo |
| Vite env variable prefix (`VITE_`) | Already done in MVP | Keeps credentials out of server-side code, in client bundle |
| Light XOR/base64 obfuscation in bundle | 20 min | Stops grep/string search; trivial to reverse with DevTools |
| Nothing for the session string | — | Session lives in localStorage / later IndexedDB; protected by OS-level browser profile encryption, which is not your app's responsibility |

**Recommendation: create your own free api_id at `my.telegram.org` (2 minutes, free), store in `.env`, done.** The `.env` approach is what every Telegram client does. It is sufficient and appropriate.

## 3. Framework: Preact vs Svelte for this specific project

You asked for more information. Here is a direct comparison for a gallery app with Vite + TypeScript.

**Preact**

```tsx
// component looks like React
function GalleryGrid({ dialog }: { dialog: Dialog }) {
  const [photos, setPhotos] = useState<MediaItem[]>([]);
  const [selected, setSelected] = useState<Set<number>>(new Set());

  return (
    <div class="grid">
      {photos.map((p, i) => (
        <PhotoItem key={p.id} item={p} selected={selected.has(i)}
          onSelect={() => toggleSelect(i)} />
      ))}
    </div>
  );
}
```

- Runtime: 3 KB. Never disappears, always there.
- Ecosystem: React libraries work (PhotoSwipe has React bindings).
- TypeScript: first-class, JSX types built in.
- Animations: need CSS or a library.

**Svelte**

```svelte
<!-- GalleryGrid.svelte -->
<script lang="ts">
  import { photos, selected } from '../stores';
</script>

<div class="grid">
  {#each $photos as photo, i (photo.id)}
    <PhotoItem item={photo} selected={$selected.has(i)}
      on:select={() => selected.update(s => { s.add(i); return s; })} />
  {/each}
</div>
```

- Runtime: 0 KB. Compiles away.
- Ecosystem: smaller. No PhotoSwipe Svelte binding (use vanilla PhotoSwipe directly — fine).
- TypeScript: supported, but TS inside `.svelte` files has minor rough edges.
- Animations: `transition:fade`, `transition:slide`, `animate:flip` built in — natural for gallery.

**For this project specifically:**

The gallery is media-heavy with frequent DOM updates (thumbnails loading in, selection state). Svelte's compile-time reactivity handles this without a virtual DOM diffing pass. For a grid of 200+ items that updates frequently, Svelte's `{#each}` with keyed blocks is measurably more efficient than Preact's virtual DOM.

The built-in `transition:fly` and `animate:flip` are also directly useful — smooth item entry when new photos load, smooth reorder if you sort.

**My recommendation: Svelte.** The slightly smaller ecosystem is not a concern because we are not using a component library — everything is custom. The TypeScript rough edges are minor. The performance and built-in animation advantages are real.

If you have strong React/Preact experience and want to move faster in Phase 0, go Preact. If neither is familiar, go Svelte — the syntax is cleaner for this kind of app.
