# Playwright-Friendly UI Plan

> Status: superseded
> Reason: UI testability improvements implemented; Playwright tests now stable with 32/32 short test passes

## Decision
- Make the UI Playwright-friendly by fixing the UI first, then aligning tests to the real UI behavior.
- Keep the existing mock auth flow: `send code -> submit code`; do not add a dedicated fast-login path.
- Upgrade interaction semantics where the UI already behaves like tabs, lists, and actionable items.
- Add stable, explicit test hooks (`data-testid`) only at durable screen boundaries and repeated interactive elements.

## Why
- Current short-test failures are mostly caused by UI/test contract mismatch, not by Playwright container execution.
- The auth and dialog UIs rely on visual classes and text content, but do not expose stable semantics or durable selectors.
- Several tests currently target elements that do not exist in the UI (`role="tab"`, `data-testid="dialog-list"`) or assume the wrong auth flow.
- Improving the markup contract first produces more resilient tests and a more accessible UI.

## Current Findings

### Auth Screen
- `src/components/auth/AuthScreen.svelte`
  - The Phone / QR controls are visually tabs but are plain buttons with no tab semantics.
  - There is no stable container/test hook for the auth screen or tab list.
  - The active mode is represented only by CSS class.

### Phone Auth Flow
- `src/components/auth/PhoneForm.svelte`
  - Real mock flow is two-step: `Send Code` -> show `Verification code` -> `Submit Code`.
  - Tests currently expect login completion too early or rely on brittle text-only assumptions.
  - There are no stable hooks for auth step transitions (`phone`, `code`, `password`).

### QR Auth Flow
- `src/components/auth/QRForm.svelte`
  - Canvas exists but lacks a stable hook.
  - 2FA follow-up state exists but is not explicitly marked for tests.

### Dialog List
- `src/components/dialogs/DialogList.svelte`
  - The screen has no `data-testid` for the dialog view root or list containers.
  - The Galleries / Groups / Chats controls are visually tabs but are plain buttons with no tab semantics.
  - Search input is conditional and has no stable hook.
  - Tests currently look for a nonexistent `data-testid="dialog-list"`.

### Dialog Items
- `src/components/dialogs/DialogItem.svelte`
  - Each row is a clickable `div` with `role="button"`, but there is no stable item hook.
  - Keyboard interaction handles `Enter` only; it should also support richer semantics if kept as button-like row.
  - The add/remove action button has no stable hook per dialog.

### App Screen Boundaries
- `src/App.svelte`
  - Screen switching is driven by auth/router state, but top-level rendered screens have no explicit testing anchors.

### Current Test Mismatch
- `tests/e2e/short/auth.spec.ts`
  - Already partially adjusted away from `role="tab"`, but still depends on weak text assumptions.
- `tests/e2e/shared/fixtures.ts`
  - Expects auth transitions and dialog selectors that do not match the real UI contract.

## UI-First Implementation Scope

### 1. Add Stable Screen-Level Hooks
- Add durable `data-testid` markers for major rendered states, likely including:
  - auth screen root
  - phone auth panel
  - QR auth panel
  - dialogs screen root
  - gallery screen root
  - settings screen root if short tests depend on it
- Keep hooks small and intentional; avoid sprinkling test IDs everywhere.

### 2. Upgrade Auth Tabs To Real Tab Semantics
- In `src/components/auth/AuthScreen.svelte`:
  - convert the Phone / QR control group into a proper `tablist`
  - give each control `role="tab"`
  - wire `aria-selected`, `aria-controls`, and stable IDs
  - mark the corresponding content panels with `role="tabpanel"`
- Preserve current visual design and existing click behavior.

### 3. Make Phone Auth Steps Explicit And Testable
- In `src/components/auth/PhoneForm.svelte`:
  - expose the current step using either a root `data-testid` or `data-auth-step` attribute
  - add stable hooks for:
    - phone input
    - send code button
    - verification code input
    - submit code button
    - password input
    - submit password button
    - status text
  - keep the real mock flow intact
  - ensure step changes are reflected in markup in a way Playwright can wait on reliably
- Optional but recommended:
  - add `aria-live` to auth status text so async transitions are visible to assistive tech and test assertions

### 4. Make QR Auth Explicit And Testable
- In `src/components/auth/QRForm.svelte`:
  - add stable hooks for the QR panel, canvas, refresh button, expiry text, and 2FA section
  - ensure the 2FA password prompt has explicit labels or durable selectors

### 5. Upgrade Dialog Tabs And List Structure
- In `src/components/dialogs/DialogList.svelte`:
  - add a stable root hook for the dialogs screen
  - add proper tab semantics for Galleries / Groups / Chats (`tablist`, `tab`, `tabpanel`)
  - add stable hooks for the active list container(s)
  - add a stable hook for the search input
  - add a stable hook for the empty state
- Preserve existing store-driven filtering and routing behavior.

### 6. Make Dialog Rows Deterministic For Tests
- In `src/components/dialogs/DialogItem.svelte`:
  - add stable hooks for dialog rows and per-row action buttons
  - expose dialog identity in a deterministic attribute such as `data-dialog-id`
  - preserve click behavior while improving keyboard/accessibility semantics
- If the row remains a non-button container, ensure role/state/keyboard behavior are complete and intentional.

### 7. Add Top-Level Screen Anchors Where Needed
- In `src/App.svelte` and any short-test target screens:
  - add stable, low-noise screen anchors so tests can assert route/view transitions without depending on headings alone.

## Test Alignment Scope

### 8. Rewrite Short Tests To Match The Real UI Contract
- Update `tests/e2e/short/auth.spec.ts` and `tests/e2e/shared/fixtures.ts` to follow the real mock auth flow:
  1. open auth screen
  2. select Phone tab
  3. enter phone number
  4. click Send Code
  5. wait for code step marker
  6. enter verification code
  7. click Submit Code
  8. wait for dialogs screen marker
- Do not rely on ambiguous heading text when a direct screen marker exists.

### 9. Update Remaining Short Specs To Use Stable Hooks
- Replace brittle selectors with stable hooks for:
  - dialogs screen root
  - dialog rows
  - tab controls
  - search field
  - gallery root / viewer root / settings root as needed
- Keep test intent the same; only change how targets are located and awaited.

## Validation Plan
- Run containerized short tests after UI changes.
- If failures remain, inspect whether they are due to:
  - missing selectors/hooks
  - async state transitions not being explicitly represented
  - real app bugs unrelated to Playwright friendliness
- Prefer fixing the UI contract before loosening test assertions.

## Risks
- Upgrading tab semantics may require small CSS or focus-state adjustments.
- Adding too many test IDs would clutter markup; hooks should stay screen- and component-level.
- Some short tests may still fail due to unrelated gallery/viewer logic after auth and dialogs become stable.
- Existing LSP/type issues in unrelated files may remain out of scope unless they directly block the touched UI files.

## Recommended Execution Order
1. Add screen-level test hooks for auth and dialogs.
2. Upgrade auth tab semantics and auth-step markers.
3. Upgrade dialog tab semantics and dialog-row hooks.
4. Add any missing gallery/settings/viewer anchors needed by short tests.
5. Rewrite fixtures to follow the real mock auth flow.
6. Update short specs to use the new stable hooks.
7. Run short tests and fix only remaining UI-contract issues first.

## Acceptance Criteria
- Auth and dialog UIs expose stable Playwright-friendly hooks without introducing a special test-only login path.
- Phone / QR and Galleries / Groups / Chats controls use proper semantics consistent with their tab behavior.
- The mock auth flow is explicitly represented in markup so tests can wait on step transitions reliably.
- Short tests target stable hooks and follow the real mock auth flow.
- The UI becomes more accessible and more deterministic for automated testing at the same time.
